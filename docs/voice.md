# Голос в Budz

Оба интерфейса поддерживают запись и локальное прослушивание на HTTPS и `localhost`. По команде «Расшифровать» Budz отправляет запись своему API. Budz добавляет готовый текст в черновик. Пользователь может его отредактировать перед отправкой. Для чтения ответов браузер выбирает установленный голос подходящего языка с `localService=true`.

## Режимы распознавания

Администратор задаёт режим и лимиты через окружение API. Для Docker переменные перечислены в [`.env.example`](../.env.example). Локальные значения хранятся в `.env` или передаются из хранилища секретов на сервере.

| `VOICE_MODE` | Поведение |
| --- | --- |
| `Disabled` | Сервер сообщает, что расшифровка недоступна. Запись и прослушивание работают локально |
| `Demo` | Сервер проверяет и декодирует реальное аудио, затем возвращает предсказуемую русскую фразу. Только для Development |
| `OpenAI` | Сервер отправляет подготовленный WAV в файловый API GPT-Transcribe. Переменная `VOICE_OPENAI_API_KEY` задаётся только на сервере |

GPT-Transcribe выбран для коротких многоязычных файлов. Он принимает подсказку русского языка, поддерживает автоопределение и возвращает определённый язык, если он распознан. По опубликованному тарифу стоимость составляет $0.0045 за минуту. Для файлового распознавания OpenAI указывает отсутствие хранения в состоянии приложения и журналах мониторинга злоупотреблений. [Модель и тариф](https://developers.openai.com/api/docs/models/gpt-transcribe) · [Обработка данных](https://developers.openai.com/api/docs/guides/your-data)

При запуске в Docker `ffmpeg` и `ffprobe` уже входят в образ API. При запуске API напрямую обе команды должны быть в `PATH`. Сервер проверяет контейнер и кодек, длительность и наличие аудиосигнала, декодирует запись в монофонический WAV с частотой 16 кГц. Поддерживаются WebM/Opus, Ogg/Opus и MP4/AAC с одной звуковой дорожкой. Временные данные удаляются после обработки или отмены.

## Запуск и проверка

1. Задайте `VOICE_MODE=Demo` в локальном окружении и выполните `docker compose up -d --build --wait api frontend`.
2. Войдите в Budz. В диалоге запишите короткую фразу, выберите «Завершить запись» и «Расшифровать». В черновике появится «Это тестовая расшифровка Budz.».
3. Для живой проверки задайте `VOICE_MODE=OpenAI` и серверный секрет `VOICE_OPENAI_API_KEY`, затем пересоздайте контейнер API. Повторите сценарий с русской фразой, сравните результат с произнесённым текстом. Проверьте русский язык и автоопределение.

Авторизованный `GET /api/v1/voice/capabilities` возвращает `available`, языки, типы записей и фактические лимиты. При отсутствии ключа в режиме OpenAI значение `available` равно `false`. Прямой запрос принимает `multipart/form-data` с одним полем `audio` и необязательным `language` со значением `ru` или `auto`. В примере токен берётся из переменной `BUDZ_ACCESS_TOKEN`.

```bash
curl -H "Authorization: Bearer $BUDZ_ACCESS_TOKEN" \
  http://localhost:8080/api/v1/voice/capabilities
curl -H "Authorization: Bearer $BUDZ_ACCESS_TOKEN" \
  -F "audio=@recording.webm" -F "language=ru" \
  http://localhost:8080/api/v1/voice/transcriptions
```

Успешный ответ содержит `text` и необязательный `language`. Формат, размер, длительность, тишина и ошибки запроса дают отдельные коды. Сервер сообщает о занятой операции кодом `voice_active`, о превышении частоты кодом `voice_rate_limit` и заголовком `Retry-After`. Коды `voice_timeout` и `voice_unavailable` различают тайм-аут и недоступность провайдера.

| Переменная Compose | Значение по умолчанию |
| --- | --- |
| `VOICE_MAX_SECONDS` | 120 секунд |
| `VOICE_MAX_BYTES` | 12 582 912 байт (12 МиБ) |
| `VOICE_STARTS_PER_MINUTE` | 6 попыток на аккаунт |
| `VOICE_TIMEOUT_SECONDS` | 45 секунд на проверку и распознавание |

На одном экземпляре API разрешена одна активная расшифровка на аккаунт. При горизонтальном масштабировании единые лимиты требуют общей инфраструктуры ограничений. Журналы Budz содержат HTTP-статусы и служебные параметры. Аудио, имя загруженного файла и распознанный текст исключены из журналов.
